# Руководство: как выполнить практику

Идите по шагам. После каждого шага запускайте `python -m pytest -v` и `python tools/self_check.py`.
Рядом указаны блоки лекции (презентация `testing_deck/index.html`), где разобрана тема.

**Главная идея всей работы:** тест нужен не чтобы быть зелёным, а чтобы **покраснеть, когда код сломан**.
Поэтому для каждого теста задавайте себе вопрос: *«какую поломку он поймает?»*

## Шаг 0. Подготовка (10 минут)

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
python -m pip install -r requirements.txt
python -m pytest -v
```

Тесты красные — это нормально: реализация ещё не написана (`NotImplementedError`).
Откройте `app/ports.py`: это **контракты** зависимостей сервиса. Сервису важно, что репозиторий умеет
`get/add/list_for_user`, а уведомитель — `send`, но не как они устроены (см. лекцию).

## Шаг 1. Расчёт цены (лекция: блоки 1–3 — AAA, классы эквивалентности, границы, parametrize)

**Файлы:** `app/pricing.py`, `tests/test_pricing.py`. **Цель:** научиться писать тесты на границы и ошибки.

### Правила
- `calculate_discount(price, percent)` — уже написана. Скидка 0…100 %, иначе `ValueError`; результат округляется до копеек **half-up**.
- `volume_discount_percent(quantity)`: 1–9 шт → 0 %, 10–49 → 5 %, 50+ → 10 %; `quantity ≤ 0` → `ValueError`.
- `calculate_total(unit_price, quantity)`: цена × количество, затем скидка за объём.

### Как делать
1. **Сначала тесты, потом код** (красный → зелёный). Допишите `tests/test_pricing.py` по списку из его docstring.
   Тесты на `volume_discount_percent` и `calculate_total` упадут с `NotImplementedError` — это правильный «красный» старт.
2. Реализуйте две функции. Каждая — несколько строк; `calculate_total` вызывает две другие функции.
3. Добейтесь зелёного прогона.

### Как придумывать случаи (блок 2 лекции)
Для правила «от 10 штук — 5 %» проверяйте **соседей границы**: 9, 10, 11. Для «от 50» — 49, 50, 51.
Ошибки `>` вместо `>=` ловятся только на самой границе.

```python
@pytest.mark.parametrize("quantity, percent", [(9, 0), (10, 5), ...])   # допишите
def test_volume_discount_boundaries(quantity, percent):
    assert volume_discount_percent(quantity) == percent
```

### Округление (блок 2 лекции)
`Decimal` не «теряет копейки», но результат всё равно надо округлять. Найдите вручную случай, где после скидки
получается ровно «полкопейки»: например, `9.90 × 95 % = 9.405`. По правилу half-up это `9.41`, а «банковское» округление
дало бы `9.40`. Если ваш тест не содержит такого случая, он не заметит смены режима округления.

### Типичные ошибки
- Сравнивать `Decimal` с `float` (`== 950.0`) — пишите `Decimal("950.00")`, **строкой**.
- Считать ожидаемое значение тем же выражением, что в коде. Считайте вручную и записывайте число.
- Проверять `pytest.raises(Exception)` вместо `ValueError`: такой тест поймает и опечатку в коде.

**Баллы:** реализация 8, мутации 10, структура 2 (≥2 теста с `parametrize` и ≥2 проверки `pytest.raises`).

## Шаг 2. Сервис заказа: DI, fake, фикстуры (лекция: блоки 3–4 — фикстуры, зависимости и DI)

**Файлы:** `app/service.py`, `tests/fakes.py`, `tests/conftest.py`, `tests/test_order_service.py`.

### Идея
`OrderService` **не создаёт** репозитории сам, а получает их в конструкторе (`__init__`). В приложении сюда
передадут реальные, в тесте — упрощённые (**fake**): словарь вместо базы. Контейнер для этого не нужен (блок 4 лекции).

### Как делать
1. **Реализуйте `place_order`** по порядку из его docstring (шаги 1–6; уведомление пока можно не вызывать).
   Порядок важен: сначала проверяются входные данные, потом товар, потом склад, и только потом — сохранение.
2. **Допишите `FakeOrderRepository`** в `tests/fakes.py`. Он должен вести себя как база: первому заказу даёт `id=1`,
   второму — `2`; `get` возвращает заказ или `None`; `list_for_user` — заказы пользователя по возрастанию `id`.
3. **Напишите фикстуры** в `tests/conftest.py` (не менее трёх). Фикстуры зависят друг от друга по имени аргумента:

```python
@pytest.fixture
def service(products, orders, notifier):      # pytest сам найдёт products, orders, notifier
    return OrderService(products, orders, notifier)
```
4. **Тесты** по списку из `tests/test_order_service.py`.

### Что значит «проверить заказ»
Мало написать `assert order.total == ...`. Заказ должен реально **попасть в репозиторий**; ошибка не должна оставить
в репозитории «мусор». Проверяйте состояние fake после вызова: `assert orders.get(order.id) == order`,
`assert orders.all == []` (в свой fake добавьте удобное свойство для этого).

### Граница склада
Склад — 5, заказ — 5: допустимо. Заказ — 6: `OutOfStock`. Нужны **оба** теста; тест только на «склад пуст» не поймает
ошибку `<` вместо `<=`.

### Параметризованный расчёт суммы
Одно правило — много примеров (блок 3 лекции). Возьмите товар с ценой `0.99` и запасом 100, количества 1, 9, 10, 49, 50, 100
и ожидаемые суммы, посчитанные вручную (или калькулятором, но **не кодом приложения**).

### Типичные ошибки
- Фикстура с `yield` и `return` одновременно: в функции-генераторе `return x` **ничего не отдаёт** тесту. Пишите `yield x`.
- Тест зависит от порядка выполнения или от общего изменяемого объекта: создавайте новые fake в каждой фикстуре (область `function`, блок 3 лекции).
- Проверка только исключения без проверки побочных эффектов («заказ не сохранён»).

**Баллы:** реализация 10, мутации 14, структура 6 (≥3 фикстуры, 2 fake с `get`, `parametrize` в тестах сервиса).

## Шаг 3. Уведомления: spy, stub, mock (лекция: блок 5 — двойники)

**Файлы:** `app/service.py` (метод `_notify`), `tests/fakes.py`, `tests/test_notifications.py`.

### Правила
- После успешного заказа уходит **ровно одно** сообщение пользователю `user_id`; в тексте — номер заказа и сумма.
- При `ProductNotFound`, `OutOfStock`, `InvalidQuantity` сообщений **нет**.
- Если `send` упал — заказ **остаётся сохранённым**, ошибка не пробрасывается (в лог идёт предупреждение).
- Если упал репозиторий заказов — исключение идёт наружу, сообщений нет.

### Как делать
1. Допишите `NotifierSpy` (запоминает `(user_id, text)`), `FailingNotifier` (бросает `TimeoutError`), `BrokenOrderRepository`.
2. Реализуйте `_notify` и вызовите его в `place_order` **после** сохранения заказа.
3. Тесты. Один из них напишите через `unittest.mock`:

```python
notifier = Mock(spec=Notifier)                 # spec — нельзя вызвать несуществующий метод
notifier.send.side_effect = TimeoutError("нет ответа")
service = OrderService(products, orders, notifier)
order = service.place_order(...)               # не должно упасть
notifier.send.assert_called_once()
```

### Две ловушки, которые проверяет автопроверка
1. **Совпадающие числа.** Если в тесте `user_id=1` и `product_id=1`, тест не заметит, что уведомление ушло по `product_id`.
   Берите разные значения: `user_id=42`, `product_id=7`.
2. **«Список не пуст».** `assert notifier.messages` пропустит двойную отправку. Пишите `assert len(notifier.messages) == 1`.

**Баллы:** реализация 5, мутации 8, структура 2 (есть spy/Mock и есть «падающий» уведомитель).

## Шаг 4. SQLite и контрактные тесты (лекция: блок 7 — базы данных; блок 4 — контракты)

**Файлы:** `app/sqlite_repo.py`, `tests/conftest.py`, `tests/test_order_repository.py`.

### Идея
Fake — упрощение, оно не доказывает корректность SQL. Чтобы проверить SQL, берём настоящую SQLite
(`":memory:"` — база в оперативной памяти, создаётся и исчезает за доли секунды). Один и тот же набор тестов
запускаем **и для fake, и для SQLite** (контракт): если оба зелёные, fake ведёт себя как реальное хранилище.

### Как делать
1. Реализуйте `_to_order`, `add`, `get`, `list_for_user`. Параметры в SQL — только через `?`:

```python
cursor = conn.execute("INSERT INTO orders (user_id, ...) VALUES (?, ?, ...)", (order.user_id, ...))
conn.commit()
order_id = cursor.lastrowid
```
   Сумма хранится **текстом**: `str(order.total)` при записи, `Decimal(row[4])` при чтении. Если сохранить как `float`, копейки «поплывут».
2. Фикстуры в `conftest.py`:

```python
@pytest.fixture
def conn():
    connection = sqlite3.connect(":memory:")
    init_schema(connection)
    yield connection          # до yield — подготовка
    connection.close()        # после — очистка (блок 3 лекции)

@pytest.fixture(params=["fake", "sqlite"])
def order_repo(request, conn):
    ...                       # верните нужную реализацию по request.param (не return+yield в одной функции!)
```
   Любой тест с аргументом `order_repo` выполнится **дважды**.
3. Тесты по списку из `tests/test_order_repository.py`. Пометьте файл `pytestmark = pytest.mark.integration`.
4. **Отдельный тест только для SQLite:** прямая вставка строки с `quantity = 0` должна дать `sqlite3.IntegrityError`.
   Fake такого ограничения не имеет — вот что значит «fake не доказывает корректность SQL».

### Типичные ошибки
- Проверять список заказов, когда в репозитории заказы только одного пользователя: фильтр по `user_id` не проверен.
- Один заказ в «списке»: порядок не проверен. Нужно минимум два заказа одного пользователя.
- Сравнивать `Decimal` из базы с `float`.

**Баллы:** реализация 8, мутации 10, структура 2 (параметризованная фикстура/тест и маркер `integration`).

## Шаг 5. Покрытие, Allure, CI (лекция: блоки 8–9)

### 5.1 Покрытие (≥ 90 % по веткам — 6 баллов)

```bash
python -m pytest --cov=app --cov-branch --cov-report=term-missing --cov-report=html
```
`term-missing` покажет номера непокрытых строк, `htmlcov/index.html` — подсветку в браузере. Помните (блок 8 лекции):
покрытие показывает лишь, что код **выполнялся**; качество проверок оценивают мутации.
Сделайте скриншот сводки в `docs/coverage.png`.

### 5.2 Allure (скриншот отчёта — `docs/allure.png`)

```bash
python -m pip install allure-pytest
python -m pytest --alluredir=allure-results
allure serve allure-results
```
Установите Allure CLI отдельно ([инструкция](https://allurereport.org/docs/install/)). Чтобы флаг подставлялся автоматически,
добавьте `--alluredir=allure-results` в `addopts` файла `pytest.ini`. Одной командой всё делает `./run_tests.sh`.

### 5.3 Маркеры (`pytest.ini`, 2 балла)
Маркеры `unit` и `integration` уже зарегистрированы (`--strict-markers` ругнётся на опечатки).
Пометьте тесты: `pytestmark = pytest.mark.unit` — быстрые, `integration` — с SQLite. Теперь можно запускать по отдельности:

```bash
python -m pytest -m unit
python -m pytest -m integration
```

## Мутационная самопроверка (делайте перед сдачей!)

Так же, как автопроверка, проверьте свои тесты вручную. Для **каждого** пункта: внесите поломку в `app/`,
запустите `python -m pytest`, убедитесь, что **какой-то тест покраснел**, и верните код обратно (`git checkout app/`).

| Поломка | Должен упасть тест на… |
|---|---|
| в `volume_discount_percent` заменить `>=` на `>` (обе границы) | границы 10 и 50 |
| в `calculate_discount` сменить `ROUND_HALF_UP` на `ROUND_HALF_EVEN` | округление |
| в `place_order` заменить `stock < quantity` на `stock <= quantity` | заказ на весь остаток |
| убрать вызов `self._orders.add(...)` | заказ сохраняется в репозиторий |
| в `_notify` отправлять `order.product_id` вместо `user_id` | получатель уведомления |
| вызвать `_notify` дважды | число сообщений |
| убрать `try/except` в `_notify` | падающий уведомитель |
| в SQL `list_for_user` убрать `WHERE user_id = ?` | фильтр по пользователю |
| в SQL заменить `ORDER BY id` на `ORDER BY id DESC` | порядок |
| в схеме убрать `CHECK (quantity > 0)` | тест `IntegrityError` |

Тест не покраснел → добавьте проверку, которой не хватало. Запишите в `REPORT.md` три примера.

## Бонус: идемпотентность (лекция: блок 6 — «Идемпотентность»)

Клиент мог не получить ответ и **повторить** запрос. Платёж или заказ при этом не должны задвоиться.
Реализуйте `request_id` в `place_order` (словарь `request_id → Order` внутри сервиса; в настоящей системе нужен уникальный
индекс в базе). Напишите тесты в `tests/test_idempotency.py` (см. docstring). Дополнительно (до +5 вручную):
прогнать контрактные тесты на PostgreSQL в Docker/Testcontainers либо Allure с сохранением истории между запусками.

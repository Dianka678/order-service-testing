# Практика: сервис оформления заказа

Сквозной пример лекции «Тестирование Python-приложений»: каталог товаров → заказ → уведомление.
Вы **реализуете** небольшой сервис и **пишете тесты** к нему. Оценивается и то и другое — причём
тесты проверяются не «на количество», а по тому, замечают ли они намеренные поломки кода.

> Пошаговые пояснения «как делать» — в **[GUIDE.md](GUIDE.md)**. Читайте его по шагам вместе с работой.

## Что понадобится

- Python 3.10+ (проверено на 3.13), `git`
- `python -m venv .venv` → активировать → `python -m pip install -r requirements.txt`
- Для отчёта Allure (шаг 5): [Allure CLI](https://allurereport.org/docs/install/) — ставится отдельно

```bash
python -m pytest -v                       # все тесты
python -m pytest spec -q                  # примеры из задания (спецификация)
python tools/self_check.py                # самопроверка перед сдачей
./run_tests.sh                            # тесты + покрытие + Allure (Windows: run_tests.bat)
```

## Что уже есть, а что делаете вы

| Файл | Статус |
|---|---|
| `app/models.py`, `app/errors.py`, `app/ports.py` | готово, **не менять** (модели, ошибки, контракты зависимостей) |
| `app/pricing.py` | `calculate_discount` готова; **`volume_discount_percent`, `calculate_total` — ваши** |
| `app/service.py` | **`OrderService.place_order` и `_notify` — ваши** |
| `app/sqlite_repo.py` | схема готова; **методы репозитория — ваши** |
| `tests/` | **ваши тесты**: в каждом файле — пример и список того, что нужно покрыть |
| `spec/test_examples.py` | публичные примеры, по ним можно сверить реализацию |
| `tools/` | `self_check.py` — самопроверка; `structure_checks.py` — что именно проверяется в структуре |

**Имена файлов в `tests/` менять нельзя**: проверяющая система находит их по именам
(`test_pricing.py`, `test_order_service.py`, `test_notifications.py`, `test_order_repository.py`,
бонус — `test_idempotency.py`) и подставляет в них свою версию `app/`. Поэтому тесты должны
использовать только публичные модули из `app/` и ваши `tests/fakes.py`, `tests/conftest.py`.

## Шаги и баллы (основная часть — 100 баллов)

| Шаг | Что делаете | Реализация | Тесты* | Структура | Всего |
|---|---|---|---|---|---|
| 1. Расчёт цены | тесты на скидки, границы, округление; реализация `volume_discount_percent` и `calculate_total` | 8 | 10 | 2 | **20** |
| 2. Сервис заказа | fake-репозитории, фикстуры, параметризация; реализация `place_order` | 10 | 14 | 6 | **30** |
| 3. Уведомления | spy, stub, `Mock`; ошибки зависимостей; реализация `_notify` | 5 | 8 | 2 | **15** |
| 4. SQLite | репозиторий на SQL, контрактные тесты для fake и SQLite | 8 | 10 | 2 | **20** |
| 5. Инфраструктура | покрытие ≥ 90% (ветки) — 6; CI — 3; маркеры в `pytest.ini` — 2; `REPORT.md` — 2; скриншоты Allure и coverage — 2 | — | — | — | **15** |
| Бонус | идемпотентность по `request_id` (реализация 2 + тесты 3); PostgreSQL/Testcontainers или Allure с историей — до 5 вручную | | | | **+10** |

\* **Как оцениваются ваши тесты.** Проверяющая система берёт эталонную реализацию, по одной вносит в неё
небольшие поломки («мутации»: сдвинуть границу, убрать проверку, отправить уведомление не тому пользователю…)
и запускает **ваши** тесты. Мутация, на которой ваши тесты упали, — «убита» и приносит баллы.
Если тесты остались зелёными — вы не проверяли это поведение. Тесты, красные на эталоне, не оцениваются
вообще (значит, они ожидают неверное поведение). Баллы за реализацию — по скрытым тестам, которые
запускаются на вашем `app/`.

Оценка по 10-балльной шкале = набранные баллы / 10 (с учётом бонуса, но не больше 10).

## Как сдавать

1. Работа в git-репозитории; сдача — ссылка на репозиторий (ветка `main`) + Pull Request с вашей работой.
   Хотя бы один однокурсник делает ревью PR (комментарии по тестам: что они проверяют, а что нет).
2. В репозитории: код, тесты, `pytest.ini`, `.github/workflows/tests.yml`, `REPORT.md`,
   `docs/allure.png` и `docs/coverage.png`.
3. Перед сдачей — `python tools/self_check.py` и зелёный CI.
4. Преподаватель запускает автопроверку и присылает отчёт: что убито, что выжило и почему это важно.

## Честная работа

Тест, который лишь повторяет реализацию («`assert total == price * quantity`» там, где реализация делает ровно это),
не защищает от ошибок: ожидаемые значения считайте вручную, по правилам из условия. Общие идеи обсуждать можно,
код и тесты — свои. Использование ИИ-помощников допустимо, если вы можете объяснить каждый тест и каждую
мутацию, которую он ловит (эти вопросы задаются при защите).
